F-01 · Agentic AI Requirements Toolkit

Agentic Requirements Stack

Six layers that define what a complete specification means for a system that chooses its own steps.

01 · What problem it solves

Traditional functional requirements answer one question — what should the system do? An agent that plans, selects tools, and adapts at run time cannot be specified by enumerating steps, because the agent constructs its own steps. Teams that specify agents as feature lists routinely ship with most of the actual control surface undefined: nothing states what the agent may write to, which APIs it may call and at what rate, what happens when its confidence is low, what it may remember across sessions, or what evidence would satisfy an auditor after the fact.

The Stack reorganizes completeness. An agentic specification must answer six questions, arranged as layers, each building on the one beneath it. Scored against a draft specification, it produces a gap table — typically revealing that a feature-oriented spec addresses only the first layer, and partially.

02 · How it works

Score each layer 0–2: 0 not addressed, 1 partially specified or ambiguous, 2 reviewable, testable, owned, and evidenced. Every layer below 2 gets an owner and a closure action. High-impact use cases should set a release threshold of no layer below 2.

LayerKey question
1 — GoalWhat outcome is the agent accountable for, under what constraints, measured how?
2 — Autonomy boundariesWhat may it do, what must it ask about, and what is prohibited?
3 — Tool contractsFor each capability, what actions, preconditions, side effects, and limits apply?
4 — Escalation & handoffWhen does control return to a human, to whom, with what payload and timeout?
5 — Memory & data rightsWhat may it retain, learn from, combine, or disclose across sessions and contexts?
6 — Audit & traceabilityWhat evidence must exist to reconstruct and defend every consequential action?

The full template additionally carries a Memory & Data Rights register (layer 5) and a Verification & Release Readiness checklist (layer 6), so a completed Stack assessment ends in a signed release decision with residual risks visible.

03 · Worked example

A national retailer pilots an agent that processes online return requests: it verifies eligibility, issues refunds within policy, and escalates disputes. Scoring the pilot's three-page draft spec against the Stack:

LayerScoreGap foundAction
1 Goal1“Reduce returns handling effort” — no quality, latency, or cost measureAdd measurable outcome set; owner: product
2 Boundaries0No refund-value threshold; unclear if agent may override restocking feesRun Autonomy Boundary Canvas workshop
3 Tool contracts0Refund API and inventory writeback undocumentedDraft contracts for all 6 candidate tools
4 Escalation1“Escalates disputes” — no recipient, payload, or timeout definedComplete Escalation & Handoff Matrix
5 Memory / data0Unstated whether agent may reuse one customer's return pattern on anotherDefine retention and combination rules
6 Audit0No evidence record for “why was this refund issued”Start Traceability Ledger

Total 2 of 12. The pilot proceeds only after layers 2, 3, and 4 reach score 2 for the release population.
